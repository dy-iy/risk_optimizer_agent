# EDOS_improve 改造方案（待审核）

本文件记录完整改造方案。已按单独指示完成路径修正和四状态修改策略：判定阈值仅在总控中设置，策略在工作流计算一次。Analyzer 仅返回 action、operations，每项只含 target、evidence、plan，Patcher 按 plan 实现。用户明确本阶段不接通 stop；仍保留每轮最多 5 项操作，未启用下文拟议的 3 项上限、样本支持量门槛、开发集拆分、模式分组、接受/回滚和运行目录隔离。

下文尚未实现的内容仍为待审核方案；策略的当前实现以 README 和 orchestrator.py 为准。当前已明确：低覆盖高准确率仅新增，高覆盖低准确率仅修改，高覆盖高准确率可新增或修改，低覆盖低准确率仅修改。后文原始提案中的 delete 和 stop 不在当前实施范围。现有 LF、数据和历史结果未因此更改，验证使用模拟模型调用。

当前反馈已进一步调整为按操作抽样：add 只给两组未覆盖样例，各最多 2n；modify 只给验证错例、验证正确及训练冲突三组，各最多 n。策略先确定 selected_action；双操作状态有覆盖缺口选 add，完全覆盖后选 modify。add 的 Analyzer/Patcher 提示词要求多例共享模式及泛化机制，禁止逐例生成 LF；这属于提示词约束，尚未接入下文拟议的实际收益验收。

目标：让低覆盖、高精度阶段优先发现并验证新的可靠覆盖，同时保留对误标、旧正确行为损失和类别退化的约束。

历史完整验证集已经参与过旧实验，因此该划分是对本次新运行的信息隔离，不是一个从未被历史实验使用过的新数据集。测试集始终不参与操作、验收、回滚、停止或选版。

## 5. 反馈：从随机弃权样例到模式分组

### 5.1 明确三种状态

- `uncovered`：全部 LF 返回 -1，需要发现新模式。
- `tied`：存在有效票但最高票并列，需要分析冲突或表决结构。
- `wrong`：已输出类别且与开发金标不符，需要分析误标。

同时保存 LF 并集覆盖率和简单投票输出覆盖率。优化收益按实际输出计算，不能用“多投了几票”代替“多产生了正确预测”。

### 5.2 新增 uncovered_analysis

拟提供以下内容：

- 训练集和反馈开发集的未覆盖数量、比例。
- 反馈开发集按类别的未覆盖数量和比例。
- 当前训练弱标签的类别票量、类别输出量、弃权量。
- 模式组 ID、训练支持量、开发金标支持量、代表文本、近似反例、候选关键词/短语。
- 每个样例明确标记 `train_unlabeled` 或 `feedback_gold`；不为训练样例伪造正确标签。

首版使用本地词/字符 TF-IDF 与 MiniBatchKMeans，称为词面模式分组，不宣称已经实现语义理解。不下载句向量模型，不增加模式发现阶段的 LLM 请求。

TF-IDF 仅拟合训练正文并按训练数据哈希缓存；对未覆盖训练样本聚类，将反馈开发集未覆盖样本分配到相近模式组。没有训练支撑的开发模式单独标记，降低优先级，防止只补开发集模板。

初始最多聚成 12 组，每轮提供最多 6 组；每组最多 5 个代表样例、3 个相近的其他类别开发反例。小数据量时降低组数。两个类别都有可靠模式组时，分别保留候选名额，避免大类独占反馈预算。

## 6. 决策：目标由程序确定，LLM 选择具体模式和规则

初始定义：

- `C = min(训练简单投票输出覆盖率, feedback_valid 简单投票输出覆盖率)`。
- `Q = feedback_valid 已输出样本准确率`。
- 已输出开发样本少于 30 条时，将精度状态标记为“证据不足”，不因几条全对就认定高精度。

| 状态 | 程序确定的目标 | 允许操作 |
| --- | --- | --- |
| C < 0.8，Q >= 0.9，支持量足够 | 扩大可靠覆盖 | 仅 add |
| C < 0.8，Q < 0.9，支持量足够 | 优先修复高影响误标 | 仅 modify |
| C >= 0.8，Q < 0.9 | 提升规则质量 | 仅 modify |
| C >= 0.8，Q >= 0.9 | 精细补充剩余模式 | add / modify |
| 精度证据不足 | 保守探索新覆盖 | 小批 add / 扩展型 modify |

没有可靠模式时允许停止，不能为了满足轮数强行生成宽泛规则。覆盖和精度达标也不自动意味着必须停止。

高精度、低覆盖阶段，所有 modify 均会被本地校验拒绝；高覆盖、低精度阶段，所有 add 均会被拒绝。delete 与 stop 不在当前契约中，按现有机制将具体错误交 Analyzer 纠正一次。

拟议模式分组阶段每轮只选一个模式组、最多操作 3 个 LF；当前仍保留 5 项上限与同轮统一 action。新增模式选择 add；扩展型 modify 只能在当轮策略允许时选择。

## 7. Analyzer 与 Patcher 的操作契约

只保留一种操作分类：`action=add` 或 `action=modify`。顶层只有 `action`、`operations`；每项只有 `target`、`evidence`、`plan`。匹配范围、保留行为与弃权边界统一写在 plan 中，不另分操作子类型，也不要求重复陈述原因和摘要。

示意输出：

```json
{
  "action": "add",
  "operations": [
    {
      "target": "lf_sexist_professional_exclusion",
      "evidence": ["提供的模式组、开发金标及训练支持量"],
      "plan": "识别针对女性群体的职业资格否定，输出 1；反驳、引用后否定及无性别指向的个人工作评价继续弃权，未命中返回 -1"
    }
  ]
}
```

Patcher 当前只接收原代码和通过校验的计划；后续若实施模式分组，所需代表样例与反例应在 evidence 和 plan 中明确传递。仍只输出目标函数，未涉及函数保持原样，保留局部合并、禁止整句查表、禁止文件/网络访问、共享代码不得绕过操作预算等约束。

Python 校验字段、目标、操作类型和预算；真实效果交由候选评估判断。当前不支持 stop，也不接受空 operations。

## 8. 评估与接受规则

新增 `tools/acceptance.py`，由真实预测和开发金标计算以下数量，不使用 LLM 的估计收益：

- G：旧预测弃权，新预测正确。
- E：旧预测弃权，新预测错误。
- R：旧预测错误且非弃权，新预测正确。
- L：旧预测正确，新预测错误或弃权。
- 新增正确预测净收益：`G + R - L`。
- 新覆盖部分准确率：`G / (G + E)`，分母为 0 时记为无新增覆盖，不能记成 100%。
- 两类分别统计上述变化，以及 LF 覆盖、输出覆盖、Precision/Recall/F1、冲突和训练弱标签量变化。

复用 impact 的对齐和变化计算，反馈开发集与验收开发集分别计算。接受判定使用验收开发集，训练集只提供无金标覆盖约束。

### 8.1 扩覆盖模式的初始接受条件

以下条件同时满足：

1. 训练输出覆盖率不下降，且至少增加一条非弃权训练弱标签。
2. 验收输出覆盖率增加，G > 0，且 `G + R - L > 0`。
3. 验收集全量 Macro-F1 不下降；仅为浮点比较设置极小容差。
4. 新覆盖部分整体准确率及有足够支持量的预测类别准确率均不低于 90%。
5. 旧正确预测损失 `L / N_acceptance <= 0.005`，即最多损失验收集总数的 0.5%。
6. 验收已覆盖准确率不低于 `min(0.90, 原已覆盖准确率)`；原来无输出时按 0.90 处理。

新增验收样本少于 10 条，或某个新增预测类别少于 10 条时，对该小样本部分要求无新增错误，并要求本轮没有旧正确预测损失。通过后仍标记 `evidence_strength=low`，不将小样本全对解释为已证明具有 90% 泛化精度。

这些都是供审核的初始实验门槛，不是普遍最优阈值。它们不保证显著性，也可能使少数有价值的小模式被保守处理，需要在固定开发协议下检查通过率。

### 8.2 修错模式的初始接受条件

- 验收全量 Macro-F1 和已覆盖准确率均提高。
- `G + R - L >= 0`，旧正确损失仍受 0.5% 预算约束。
- 已输出错误数减少，或正确预测净增加。
- 允许为移除有害规则降低覆盖率，但不能仅靠大量弃权制造精度提升。

候选质量不达标属于正常拒绝，不触发 Patcher 技术修复。API、文件和数据错误仍按技术错误策略停止。

验收拒绝只向下一轮 LLM 提供接受状态、粗粒度原因码，以及反馈开发集上的影响摘要；验收具体样本、类别指标和错误不进入请求。

下一轮反馈附最近尝试的模式组、action 和反馈开发集影响，避免重复提出未解决问题的同一方案；同一候选源码哈希不重复评价。

## 9. LangGraph 与版本管理

拟运行流程：

```text
评价基线 → 构造反馈/模式组 → 计算本轮目标 → Analyzer
  → stop：保存原因并结束
  → Patcher/本地删除 → 候选评价 → 影响统计 → Python 验收
      → accepted：更新当前基线
      → rejected：保持当前基线，保存候选和原因
  → 检查预算/连续拒绝次数 → 下一轮
```

`--iterations 4` 拟解释为最多尝试 4 个候选，不保证接受 4 个版本。每个候选使用独立编号，记录 `base_version` 和状态；拒绝的候选不会成为下一轮的原代码。

连续拒绝 3 轮时提前停止，防止相同反馈下反复消耗请求。Analyzer 纠正和 LF 技术修复仍分别最多一次，且只针对结构/技术失败。

候选保留为可审计实验产物，不直接删除其代码和结果。所谓回滚是“不提升候选为基线”，无需覆盖写回旧 LF。

拟新增运行输出：

```text
improve/EDOS_improve/runs/<run_id>/
├── config.json
├── dev_roles.json
├── run_state.json
├── iterations.csv
├── tokens.csv / tokens.md
└── versions/vN/
    ├── lfs.py
    ├── Snorkel/...
    ├── simple_vote/...
    └── results/
        ├── feedback.json / uncovered_groups.json
        ├── analysis.json / changes.md / errors.json
        ├── development_delta.json
        ├── decision.json
        └── attempts/round_N/...  # 保留每次真实输入和回复
```

同一基线连续被拒绝时，`results/feedback.json` 仍展示最新反馈，但每次真实请求单独归档，避免覆盖旧尝试记录。

`decision.json` 包含基线、候选、目标、接受状态、证据强度、原因码、实际收益风险、配置及开发角色哈希。迭代表与绘图区分 accepted/rejected，最佳版本仅从同一运行协议下的 accepted 候选中选择。

3. 用合成投票验证全弃权、平票、两类新增正确/错误、原正确变错误/弃权、修复以及空分母。
4. 用历史投票离线回放验收规则，逐项检查哪些候选会被接受或拒绝及原因，不执行历史 LF、不调用 API。
5. 验证 action 与程序策略的约束、一次技术修复预算、拒绝后基线不变、连续拒绝停止及恢复运行；当前不支持主动 stop。
6. 验证所有新输出位于当前运行目录；临时测试脚本和测试产物完成后清理。
7. 完成代码与离线验收后，再按明确预算开展真实对照。建议先从 v1 各尝试 4 轮进行小规模对照；正常每条流程最多 8 次 Analyzer/Patcher 请求，纠正/技术修复另计，提前停止会减少请求。

真实对照需使用相同 v1、数据角色、LLM 模型/温度、每轮 LF 上限和最大调用预算。当前流程与改进流程分别运行；记录实际 Token 和请求消耗，比较未覆盖数量、G/E/R/L、两类召回和最终 LR Macro-F1。测试指标仅在最后评价固定选定模型，不据此调整阈值。

本方案不承诺预先指定的 EDOS 分数提升；验收标准是规则扩展的真实收益可测、退化可拒绝、实验可复现，并由对照结果判断下游收益。
