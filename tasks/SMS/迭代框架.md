# LF 迭代框架

参考 `v4_widely`，沿用当前 SMS 目录结构；数据使用 WRENCH 官方固定划分。

## 实验目标（已明确）

用固定验证集的标注数据指导现有 LF 的优化，考察在有限标注成本下能否得到质量更好的 LF 和聚合结果。

## 1. 每轮流程（已确认）

Analyzer 在同一次调用中先选择本轮新增、修改或删除 LF，再分析当前版本的错例和未覆盖样本、提出具体操作 → Patcher 实现并校验，形成新版本 → 调用 `runner.py` 聚合和评价 → 记录结果，以最新可运行版本继续迭代。

## 2. 数据划分与使用（WRENCH 固定划分）

直接使用 [WRENCH 官方 SMS 数据](https://huggingface.co/datasets/jieyuz2/WRENCH/tree/d1185f6cfba8d5ace2a39229799cb3f1c136bf66/classification/sms) 的 `train.json`、`valid.json`、`test.json`，固定提交为 `d1185f6cfba8d5ace2a39229799cb3f1c136bf66`。保留官方样本归属、顺序和预处理后的正文，不按条数自行随机重分。

| 数据集 | 条数 | 保存文件 | 用途 |
| --- | ---: | --- | --- |
| 训练集 | 4,571 | `data/train.csv`，仅 `id,text` | 运行 LF，拟合 Snorkel，生成弱标签；覆盖和冲突样例不带金标 |
| 验证集 | 500 | `data/valid.csv`，含 `id,text,label` | 替代原 `labeled.csv`，向 agent 提供开发指标、错例、弃权/正确样例及 LF 质量 |
| 测试集 | 500 | `data/test.csv`，含 `id,text,label` | 每个版本用已拟合模型预测并评价，结果不反馈给 agent |

官方划分共 5,571 条；验证集为 ham 436 / spam 64，测试集为 ham 433 / spam 67。不再采用每类 50 条的均衡抽样。仓库原始 `SMSSpamCollection.csv` 保留作原始资料，但不参与当前划分、训练或反馈。

每轮只用训练集的 LF 投票矩阵调用一次 Snorkel `fit`，类别先验从固定验证集的标签比例自动估计，类别顺序为 `[ham, spam]`，当前为 `[0.872, 0.128]`。先验同时用于拟合和同一模型的预测，不再固定为 `[0.5, 0.5]`。训练金标和测试标签不参与拟合或先验估计，验证集逐样本金标不用于拟合 LF 条件概率。官方预定义 LF 投票不导入本实验。

`metrics.json` 和报告记录先验及验证集来源。`gold_used_for_fit=true` 表示验证标签通过类别先验参与拟合，并单独记录 `validation_gold_usage=class_balance_only`、训练/测试金标未参与。`iterations.csv` 增加先验来源和比例；旧结果保留原配置，按需重跑后更新对应行。

`tools/data.py` 导入官方划分，`data/split.json` 保存固定提交、源文件地址、源文件和 CSV 的 SHA-256、条数与用途。三个 CSV 已随本次调整生成，后续启动离线校验并重用；仅在三个 CSV 和清单都不存在时下载固定版本重新导入。已有划分不完整或校验失败时直接报错，不自动重新抽样。

官方数据存在相同正文跨集合的情况。为保持与基准一致，保留这一划分，不进行额外去重或按正文分组。样本编号采用 `sms_<split>_<官方编号>`，各集合编号互不重叠。

## 3. 验证集使用方式

固定同一批官方 500 条验证样本，所有轮次均从中抽取反馈样例，不新增标签。验证集金标用于估计类别先验、LF 分析与开发评价；训练集只提供无金标的覆盖/冲突信息，测试集的样本、标签和指标不进入 Analyzer 或 Patcher。

反复使用验证集优化 LF 可能对验证样本过拟合，因此最终效果使用独立测试集报告。每轮反馈样例数量仍按第 10 项限制，验证指标始终基于完整 500 条。

## 4. 数据导入与可比性

1. 从固定 WRENCH 提交读取官方训练、验证和测试文件并验证 SHA-256。
2. 保留官方正文、顺序及集合归属，训练集仅输出编号和正文，验证集和测试集保留标签。
3. 后续训练、反馈、汇总和绘图统一使用 `train` / `valid` / `test`，不再读取原 `labeled.csv` / `unlabeled.csv`。

本次重置删除旧划分、v2–v30 及旧汇总、Token 记录和图表；保留 `versions/v1/lfs.py`，以新划分重新验证 v1 基线。后续由用户重新启动实验。

## 5. 初始 LF 来源（已确认）

直接使用现有 `versions/v1/lfs.py` 中的 6 个 LF 作为 v1，后续在其基础上迭代，保留 v1 的 LF 规则。

正式迭代前，按已确认的数据划分重新评价这份 v1，分别记录验证集和测试集的基线指标；现有全量报告不直接作为新实验的基线指标。

## 6. 后续迭代方式（已确认）

保留 Analyzer 和 Patcher 两个阶段。Analyzer 在同一次 LLM 调用中先决定本轮唯一操作类型（`add` / `modify` / `delete`），再选择具体 LF 和规则思路；回复统一包含 `decision`、`overall_analysis` 和 `operations`。Patcher 根据这份分析实现下一版 `lfs.py`，交给 `runner.py` 聚合和评价。

`orchestrator.py` 中的 `LOW_COVERAGE_THRESHOLD = 0.5` 是可调整的目标切换阈值。训练集或验证集的 LF 覆盖率低于 50% 时，Analyzer 的优先目标是提高 LF 集合的整体覆盖率，让更多短信至少获得一条非弃权投票，同时控制误标风险。Agent 根据证据选择操作：可以修改已有 LF，扩展同义表达、句式或合理匹配边界，也可以新增 LF 覆盖独立模式；不预设必须新增。此阈值不作为候选通过门槛，也不保证本轮修改后覆盖率一定上升。

低覆盖时无论选择何种操作，Analyzer 都必须在 `decision.coverage_plan` 中说明覆盖不足原因、覆盖改善方案和误标控制。选择修改不再需要解释为何没有新增。删除 LF 本身不会提高集合覆盖率；若明确的有害规则需要优先删除，应说明这一安排及后续扩覆盖方向。当前只有 3 个 LF 时禁止删除。`operations` 的操作类型必须与 `decision.action` 一致，删除后至少保留 3 个 LF。不能通过默认全部判为 ham 等方式凑覆盖率。

## 7. LF 改动范围（已确认）

允许按需新增、修改、删除 LF，LF 总数可随版本变化。当前 Snorkel 聚合至少需要 3 个 LF，保留这个下限。

## 8. 单个候选版本的改动数量（已确认）

实现迭代代码时，集中写一个可手动修改的参数，默认值为 1：

```python
MAX_LF_CHANGES = 1
```

该参数限制每个候选版本相对本轮起点版本的 LF 操作总数；新增、修改、删除一个 LF 各算一项。默认值为 1 时，三种操作选其一。调整代码中的参数值即可改变上限。

先采用小步修改，便于追踪每次规则改动带来的变化；代码运行失败时按第 14 项处理。

## 9. Analyzer 输入（已确认）

- 当前 LF 代码，以及固定 500 条验证集上的评价指标。
- 完整验证集按 ham / spam 统计的样本数、LF 覆盖数和未覆盖数，以及当前覆盖率、低覆盖阈值和判定。
- 从这 500 条中选取的错例、弃权样本和部分正确样本，附真实标签、各 LF 投票及聚合预测。
- 训练集数据的覆盖率、冲突率统计，以及选出的未覆盖或投票冲突样本；这些样本只提供文本和 LF 投票，不提供真实标签。

测试集信息不进入分析过程。样例数量配置见下一项。

## 10. Analyzer 样例数量（已确认）

每次分析时，五组样例各提供最多 10 条：

| 来源 | 样例组 | 最多条数 |
| --- | --- | ---: |
| 固定验证集 | 非弃权但预测错误 | 10 |
| 固定验证集 | 聚合结果弃权 | 10 |
| 固定验证集 | 预测正确 | 10 |
| 训练集数据 | 所有 LF 均未覆盖 | 10 |
| 训练集数据 | LF 投票冲突 | 10 |

- 合计最多 50 条；某组不足 10 条时按实际数量提供，不重复凑数。
- 这只限制发给 Analyzer 的样例量。验证集指标仍基于全部 500 条，训练集统计仍基于全部训练集数据。
- 实现时集中设置可手动调整的参数：`MAX_EXAMPLES_PER_GROUP = 10`。

## 11. 候选通过指标（暂不设置，已确认）

当前先不设置基于 Macro-F1 等质量指标的通过或淘汰门槛。

每轮仍记录覆盖率、准确率、各类别 Precision/Recall/F1、Macro-F1 等评价结果。测试集不参与迭代决策。

版本推进按下一项执行，能够正常运行不代表指标一定改善。

## 12. 版本推进方式（已确认）

每次运行的起点由用户启动时指定。该次运行中，每轮保存能够正常运行的新候选，并以最新候选作为下一轮修改的起点，按版本保存各轮 LF 与指标，暂不因指标下降自动回退。

## 13. 启动交互与迭代轮数（已确认）

每次启动时按顺序询问：

1. 当前版本：本次迭代从哪个已有版本开始，例如 `v1`、`v3`。
2. 迭代轮数：本次计划追加多少轮“分析 → 修改 → 聚合评价”。

轮数由本次输入决定，不固定为 5 轮，也不包含起点版本的基线评价。起点按用户输入选择，不自动改为全局最新版本；本次运行内逐轮基于新生成的可运行版本继续。

## 14. 候选代码运行失败的处理（已确认）

候选 LF 代码出现语法、执行或返回值不符合约定等错误时，将报错反馈给 Patcher，最多额外自动修复 1 次，即首次生成加修复共最多 2 次尝试。修复仍沿用 Analyzer 本轮的决策和操作列表，不重新选择新增、修改或删除，也不改变目标函数。

仍失败则停止本次运行，保留此前成功版本、结果与报错记录。修复仍受 LF 改动数量限制；指标下降不触发这类修复。

## 15. 版本编号（已确认）

从当前 `vN` 生成下一版 `vN+1`，后续依次递增，直接写入对应版本目录，不设置覆盖检查。

例如从 `v2` 启动、追加 3 轮，依次生成 `v3`、`v4`、`v5`。

## 16. LLM 接口配置（已确认）

Analyzer 和 Patcher 共用一套模型配置，沿用 v4，从项目根目录 `.env` 读取 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL`。

`DEEPSEEK_BASE_URL` 未填写时，沿用 v4 的默认地址 `https://api.deepseek.com`。

## 17. Patcher 输出方式（已确认）

Patcher 根据 Analyzer 的建议，直接返回下一版完整的 `lfs.py`，包含普通 LF 函数和 `LFS` 列表。

程序负责保存、检查 LF 改动总数并运行评价。改动仍受 `MAX_LF_CHANGES` 限制，未涉及的 LF 逻辑保持不变。

## 18. Analyzer 输出方式（已确认）

Analyzer 在同一份 JSON 的 `decision` 中输出 `action`、`reason`、`evidence` 和低覆盖时的覆盖改善方案 `coverage_plan`，同时输出整体问题分析和建议操作列表。程序把实际覆盖率、阈值、是否低覆盖以及当前优化目标附到决策中，整份回复保存在 `analysis.json`。每项建议包含：

- 操作类型：新增、修改或删除。
- 目标 LF：已有函数名，或拟新增的函数名。
- 问题原因。
- 支持依据：已提供的样例编号、统计或代码分析。
- 具体修改思路。

实际建议执行的操作数最多为 `MAX_LF_CHANGES`，当前默认 1 项；所有操作必须属于本轮选定的同一类型。整体分析可讨论多个问题。训练集样例只能作为覆盖、冲突等观察依据，不能作为已知分类错例。

Analyzer 原始回复在解析前保存到被分析版本的 `results/analysis_raw.txt`。如果 JSON 可以解析但结构校验失败，另存 `analysis_invalid.json`，并在下一版的 `results/errors.json` 记录具体错误后停止，不自动补齐字段或重试。整体分析必须放在 JSON 顶层的 `overall_analysis` 字符串字段中；JSON 模式本身不保证这些字段符合要求。

## 19. LF 质量统计（已确认）

为每个 LF 生成一行质量统计，交给 Analyzer，并随版本结果保存：

- 验证集投票数：在固定 500 条中，该 LF 非弃权的条数。
- 验证集投票准确率：正确投票数 / 非弃权投票数；没有投票时记为“—”。该数值反映 WRENCH 官方验证集上的表现，并同时展示投票数。
- 训练集覆盖率：该 LF 在训练集数据上的非弃权条数 / 训练集总条数。
- 训练集冲突率：该 LF 投票且有其他 LF 投出不同类别的条数 / 训练集总条数。

这些统计用于诊断和报告，不作为通过或淘汰门槛。

## 20. 过程记录与版本汇总（已确认）

| 文件 | 内容 |
| --- | --- |
| `versions/vN/results/analysis.json` | 本轮操作决策、对 vN 的 LF 和开发反馈的分析，以及生成 vN+1 的修改建议 |
| `versions/vN/results/changes.md` | 从 vN-1 到 vN 实际发生的 LF 增删改，并附对应分析中的原因 |
| `iterations.csv`（SMS 根目录） | 汇总 v1 基线及后续各版的 LF 数量、500 条验证集指标、测试集指标，以及训练集数据的覆盖/冲突统计；验证集和测试集指标分列 |

各版 `report.md` 继续只展示结果，分开展示验证集和测试集指标，分析和改动说明分别保存。每个版本都保存测试结果，不额外安排起始版与最终版的单独对照。

例如，分析 v1、生成 v2 时，分析保存到 `v1/results/analysis.json`，改动记录和评价结果保存到 v2。最新版本在下一轮被分析时才生成自己的 `analysis.json`。

## 21. 模型 Token 用量统计（已确认，要求易读）

- SMS 根目录 `tokens.csv` 用中文表头按每次模型调用记录：版本、阶段、输入 Token、输出 Token、总 Token。
- 阶段区分 Analyzer、Patcher、Patcher 修复；决策用量包含在 Analyzer 的分析用量中。修复调用也计入，仍属于同一个目标版本。已有 CSV 表头保持兼容。
- 同步生成易读的 `tokens.md`，按本次启动中的各轮汇总，列出：版本、分析用量、修改用量、修复用量、本轮合计、本次累计。
- 终端使用同样的中文表格展示；易读表中的数字使用千分位，CSV 明细保留数值。本次累计与历史累计区分。
- 按 API 返回的用量记录；未返回时标为未知，易读表显示“—”，不记作 0；合计有缺失时说明仅统计了已知用量。

## 22. 程序入口与文件分工（已确认）

| 文件 | 职责 |
| --- | --- |
| `orchestrator.py`（SMS 根目录） | 启动询问版本与轮数，串联各轮迭代 |
| `tools/analyzer.py` | 组织反馈，同一次 LLM 调用完成操作决策和规则分析，校验具体操作 |
| `tools/patcher.py` | 根据分析调用 LLM，生成和校验新 LF 文件 |
| `tools/llm.py` | 模型接口调用及 Token 用量记录 |
| `tools/data.py` | 导入官方固定数据划分，后续校验并重用 |
| `tools/runner.py` | 运行单个版本的 LF、Snorkel 聚合、评价和结果保存 |

保留现有 `tools/label_model.py` 和 `tools/evaluate.py` 的聚合、指标计算分工，使用普通函数组织流程。

## 23. 反馈样例抽取方式（已确认）

五组样例分别随机抽取，每组最多 `MAX_EXAMPLES_PER_GROUP` 条，组内无放回；不足上限时全部提供。

实现时设置可手动调整的 `FEEDBACK_SEED = 42`，结合当前版本控制抽样，使相同版本、数据和配置下的反馈样例可复现。

这只决定展示给 Analyzer 的样例，不改变固定验证集、训练集数据和测试集，也不使用训练集数据的真实标签筛选样例。

## 24. 各版本测试评价（已确认）

从 v1 基线到后续每个版本，都评价同一独立测试集，并随版本保存结果；不额外安排起始版本与最终版本的单独对照。

各版本的 Snorkel 模型都只在同一训练集数据上拟合，测试时只预测，不重新拟合。测试样本、标签和指标不进入 Analyzer 或 Patcher，也不用于选择版本、调整参数或决定迭代轮数。

## 运行方法

在项目根目录启动迭代，按提示填写当前版本和追加轮数：

```powershell
python -B 'tasks/SMS/orchestrator.py'
```

输入轮数 `0` 时，只评价当前版本，不调用 LLM。追加迭代需要根目录 `.env` 中的 `DEEPSEEK_API_KEY` 和 `DEEPSEEK_MODEL`；接口地址可使用默认值。

只运行某个版本的 LF、聚合和评价：

```powershell
python -B 'tasks/SMS/tools/runner.py' --version v1
```

常用迭代参数在 `orchestrator.py` 顶部；WRENCH 固定提交、样本数量和源文件校验值在 `tools/data.py` 顶部。已有划分不会因再次启动或修改反馈随机种子而重新抽取。
